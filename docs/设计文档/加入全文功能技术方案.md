# 「加入全文」功能技术方案

> 状态：待评审（确认后再动手实现）
> 目标版本：建议 1.0.2
> 涉及范围：仅 client 侧（webview），Host 侧零改动、无需重启
> 关联讨论：`docs/列出科研场景及改进项.md` 第一优先级优化项
>
> 评审决议（2026-11-20）：
> 1. **范围选择器提前到第一期，一次做完整**——几十上百页的论文整篇 push 会撑爆上下文，章节选择不是锦上添花而是必需。
> 1b. **章节 = pdf.js 书签 / 文档标题，不是 `#` Markdown 标题**（2026-11-20 二次修正）——上一版用 `parseMarkdownHeadings()` 当章节来源，但 Zotero 抽的 PDF 全文无 `#` 标记，该方法对 PDF 文献返回空；改为复用目录浮层的 `outlineItems`，并新增"书签标题↔全文字符"定位映射。
> 1c. **功能入口固定在文献详情页，此时 PDF 已打开**（用户确认）——pdf.js 书签树必然可用，无需为"PDF 未加载"设计降级分支。范围选择器提供 4 种模式：**章节（默认优先）/ 整篇 / 字符区间 / 标题区间**，前两种之前的方式保留，给用户多几个选择。
> 2. 补「文字与图片的分流策略」（见第 8 节）：全文 chip 只管文字，图表/公式走截图 chip。
> 3. 评估「整份 PDF 直接作为附件投喂模型」的可行性（见第 9 节）：模型侧（DeepSeek V4.1-Flash）与宿主侧（DSH 0.2.1-rc.5）均具备条件，列为可选的第二条路线。

---

## 1. 要解决的问题

现状（基于源码核对）：

- 条目 chip（`item:`）提交时由 `itemText()` 展开，**只有**标题 / 作者 / 年份 / 刊物 / DOI / URL，明确不含全文、摘要、标签（`src/client/compose.ts:27-42`）。
- 想让模型读全文，目前唯一路径是帮助脚注里的 workaround：先插一条摘录（`exc:`）定位条目，再说"结合全文回答"，指望模型自己去调 `mcp__zotero__*` 工具拉正文（`src/client/locales.ts:244`）。
- 这条路径在科研场景有五个硬伤：① 依赖模型"自愿"调工具，是概率的；② MCP 可能不可用（`status.mcpOff`）或被 `disabledMcpTools` 关掉，此时 chip 里没有正文兜底，模型只拿到裸 key；③ 全文按 `FULLTEXT_MAX_BYTES = 200*1024` 截断，模型未必知道自己读到的是残篇；④ 取回的是抽取纯文本（OCR 噪声、无表格公式结构，见 `tidyAnnotation()` 的汉字插空格处理）；⑤ 多条对比时逐条拉取，延迟与 token 不可控。

**一句话目标**：把"读全文"从**模型概率性拉取（pull）**改成**用户确定性推送（push）**——正文作为消息内容的一部分，一定进上下文，且取哪段由用户在插入那一刻决定。

## 2. 关键洞察：不新增"正文自包含"的 chip

现有 7 种引用来源分两类：

- **定格类**（`exc:` / `tr:` / `shot:`）：原文/译文/出处在插入那一刻编码进 ref，自包含、不请求 Host、跨重启可展开。
- **现取类**（`item:` / `col:` / `note:` / `ann:` / `tag:` / `tags:`）：ref 只存 key，提交时由 codec 调 `fetchItem()` 现取。

**全文必须走现取类，不能走定格类**。理由：一篇正文 20 万字，若编码进 ref，草稿（会落盘）立刻膨胀到几十万字符，重放校验、剪贴板文本、历史存储全线受影响；而摘录上限 `MAX_EXCERPT_CHARS = 4000` 正是为了压住草稿体积。所以 `full:` 的 ref 只存定位信息，正文在提交那一刻现取。

这同时带来一个额外好处：全文走的是**面板自己的 `fetchItem()` HTTP 通道**（和条目 chip 同一条），**不依赖 MCP 工具**——即使 `mcp__zotero__*` 全部被禁用，全文依然能进对话。这正是上一轮分析里 pull 方案最大的漏洞，push 方案天然规避。

## 3. 方案设计

### 3.1 新增引用类型 `full:`

按项目铁律，新增一种引用来源必须同步四个文件（`reference.ts` / `cite.ts` / `compose.ts` / `useInsertion.ts`）。

**ref 格式**（只存定位，不含正文）：

```
full:<编码后的 itemKey>:<编码后的范围表达式>
```

范围表达式（决定取正文的哪一段）——**4 种模式并存，章节为默认优先**，其余三种是保留给高级/兜底场景的选择：

| 优先级 | 模式 | 语法 | 含义 | 面向 |
|---|---|---|---|---|
| ⭐ 默认 | 按章节 | `p:<起页>:<止页>:<总页>:<标题列表>` | 书签树里勾选的章节；标题 `+` 分隔、各自 `encodeURIComponent`，供提交时定位 | PDF（书签） |
| ⭐ 默认 | 按章节 | `o:<起偏移>:<止偏移>` | 快照/笔记/纯文本的章节，其 `anchorTarget().id` 就是字符偏移 | 非 PDF（标题锚点） |
| 保留 | 整篇 | `all` | 取全文（受 `FULLTEXT_MAX_BYTES` 截断） | 兜底 / 全文需求 |
| 保留 | 字符区间 | `c:<start>:<end>` | 取正文 [start, end) 字符区间 | 高级：精确控制字数 |
| 保留 | 标题区间 | `h:<起标题>:<止标题>` | 取两个 Markdown 标题之间的正文 | 高级：正文有 `#` 标记时（纯文本/Markdown 附件） |

- 所有段 `encodeURIComponent`，用 `:` 分段（沿用 `exc:` 的成熟做法，`reference.ts:220-236`）。
- `clipboardText` = `@${ref}`，无空格，满足 chip 偏移校验。
- **"按章节"是默认选中且视觉上置顶推荐的模式**，因为它最贴合用户心智；字符/标题区间收在"更多方式"里，不默认展开、不强制学习。
- `h:` 标题区间对 PDF 全文无效（抽取文本无 `#` 标记）——保留是因为纯文本/Markdown 附件确实有 `#`，且在"按章节"拿不到锚点时可作补充；UI 里对该模式给出"仅适用于含 `#` 标题的文档"提示，不隐瞒其局限。

**章节从哪来——这是本方案的关键修正**：

- PDF 的章节 = pdf.js 书签树（`PdfViewer.tsx:172` 的 `readOutline()`），也就是左上角目录浮层显示的那份，每项带 `title` 与起始 `page`。Zotero 本地 API 与集成 MCP 都没有目录端点（`outline.ts:9` 已确认），书签是唯一可靠来源。
- 快照 / 笔记 / 纯文本的章节 = 各渲染器已上报的 `DocumentOutlineItem`，其 `target` 为 `anchorTarget(字符偏移)`（`outline.ts:173-204`、`types.ts:55-57`）。
- 所以范围选择器**直接复用目录浮层同一份章节数据**——用户在目录里看到的章节名，和这里勾选的完全一致，不另造一套解析。
- **不能**用 `parseMarkdownHeadings()` 当 PDF 的章节来源：它只认 `# 标题` 标记行，而 Zotero 从 PDF 抽取的全文是纯文本流（标题就是 `2 Method` 这样的普通行），一个章节都解析不出来。上一版方案在这里判断错了。

**范围 → 全文字符区间的映射**（ref 只存小定位信息，正文提交时现取）：

- `all`：整篇，不切片。
- `c:`：偏移直取 `content.slice(start, end)`（边界 clamp 到 `[0, content.length]`）。
- `h:`：按两个 Markdown 标题在正文里定位——先 `tidy` 再 `indexOf` 找标题行；找到则切两者之间，找不到则降级整篇并在头部标注"标题未匹配，已取全文"。
- `o:`：偏移即坐标，直接 `content.slice(start, end)`。
- `p:`：Zotero 全文无分页标记（`client.ts:1253-1274` 只返回 `content/truncated/fallback`），所以走两级策略：
  1. 提交时 `fetchItem()` 取全文，把书签标题 tidy 后逐个 `indexOf` 定位；起点 = 首个被选章节标题处，终点 = 其后第一个**未被选**章节标题处（或全文末尾）。这样相邻勾选会合并成一段，跳号勾选也能切出多段。
  2. 匹配失败（书签标题与文字层编码/空格不一致，PDF 常见）→ 按 `页码 / 总页 × content.length` 估算，并在展开文本头部标注"位置为估算，建议改用整篇或字符区间"，绝不静默给出可能错位的切片。

### 3.2 数据流

```
用户点「加入全文」→ 选范围（默认章节；或整篇/字符/标题）→ 插 full: chip（草稿只存 ref，极小）
                                                          ↓ 发送
codec.serialize(ref) → fulltextCitation()
   → fetchItem(key) 取 detail.fulltext.content（现取，走面板 HTTP 通道）
   → 按范围表达式分派：all 整篇 / c: 偏移 / h: 标题匹配 / o: 偏移 / p: 标题匹配→页码估算
   → 切出所选范围的正文切片
   → fulltextText() 拼成带出处 + 范围标注 + 截断/估算声明的文本
   → wrapCitation() 包成 <zotero-ref> 块
   → 作为消息正文的一部分进模型上下文
```

### 3.3 展开文本格式（`fulltextText()`）

```
【Zotero 全文｜标题｜key=ABCD1234｜范围=章节 2 Related Work, 3 Method（P2–P8）】
（本文全文已按 200KB 上限截断，以下为节选；如需未返回部分请让用户调整上限）
<正文切片，原样，不改写>
```

- 头部带稳定 key，模型可继续用 MCP 工具交叉引用。
- **范围标注按模式取值**：章节→"章节名 + 页码"（默认模式，模型和用户都能对上"这段是第几节"）；整篇→"全文"；字符区间→"字符 4000–12000"；标题区间→"标题 X–Y"。
- 截断时**显式声明**，消除"模型不知道自己读到残篇"的隐患；定位走估算时同样显式标注。
- 展开文本声明"不含图片/图表/公式"，引导对关键图表补截图（见第 8 节）。
- 加 `<zotero-ref>` 边界，会话历史里收成胶囊（与其他 7 种一致）。

### 3.4 UI：按钮 + 范围选择器

**按钮落点**：条目详情页左上角悬浮按钮行，`加入对话` 与 `截图加入对话` 之间，新增一枚 `全文` 按钮（`SOFT_BUTTON_STYLE`，与其他按钮同高同描边）。

- 该行已有 `rowRef` + `ResizeObserver` 量宽上报、`topbarPad` CSS 变量驱动工具条让位（`InfoPanel.tsx:123,155-164`、`ItemDetail.tsx:144-147`），新增按钮会被自动计入宽度，**无需改死值**。
- 独立笔记（`itemType=note`）全文即笔记正文，`note:` 已覆盖，此按钮对独立笔记隐藏，避免与 `note:` 重复。
- 无全文索引时按钮置灰，hover 给出与 `detail.noFulltext` 一致的提示。

**范围选择器**（点按钮后弹出的小浮层，仿 `floatingBox.ts` 的浮层范式，就地锚定在按钮下方）——**4 种模式，章节默认选中、置顶推荐；其余收在「更多方式」里**：

- **默认视图「按章节」**（覆盖绝大多数场景）：
  - 列表 = 目录浮层的那份 `DocumentOutlineItem[]`（PDF 书签 / 快照 h1–h6 / 笔记标题 / 纯文本标题），按 `depth` 缩进；每行 `checkbox + 章节名 + 起始页/偏移 + 估算字数`。
  - 全选 / 清空；父子联动（勾父章节自动勾子章节，便于"精读第 3 节"一键选中其所有子节）；相邻勾选段合并。
- **「更多方式」展开后**是之前设计保留的三种，供高级/特殊场景：
  - **整篇**——取全文，兜底；
  - **字符区间**——start / end 两个数字输入框，默认 `0` 到 `min(content.length, 上限)`；
  - **标题区间**——从正文中解析出的 `#` 标题里选起止（复用 `parseMarkdownHeadings()`），带"仅适用于含 `#` 标题的文档"提示。
- 底部实时显示"已选 N 章 · 约 M 字（上限 20 万字符）"（字符区间模式则显示"字符 start–end"），确认后插 chip；字数超过上限高亮提示。
- **章节数据必然可用**：入口在文献详情页，此时 PDF 已打开、书签树已上报（用户确认的使用路径）；快照/笔记/纯文本进入详情即可解析。故不需要"PDF 未加载"的降级分支——仅当某文档确实**无书签也无标题**时，章节列表为空，此时自动切到「整篇」并提示。
- 浮层必须挂 `data-window-drag-exclude`（项目铁律，见 `floatingBox.ts`）。

**范围选择器随第一期一起交付**（评审决议）：不做"先整篇、后选择"的分期。理由：几十上百页的论文整篇 push 会直接撑爆上下文，章节选择是可用性的前提而非增强。章节列表复用现成的目录数据（`readOutline()` / `parseHtmlHeadings()`），额外成本是一个浮层 UI 和一段"章节→字符"映射；分期只会多一次 webview 刷新与回归测试，收益有限。四种范围模式共用一套映射分派，边际成本很小。

## 5. 关键取舍与风险

| 风险 | 处理 |
|---|---|
| 全文塞爆上下文 | ref 只存 key + 范围；选择器默认展开「按章节」并实时提示字数，避免一键灌整篇；字符区间模式也显示字数 |
| 书签标题对不上全文文字层（PDF 编码/空格差异，常见） | `fulltextRange.ts` 两级定位：标题 tidy 后 `indexOf` 匹配 → 失败按页码比例估算；估算时展开文本显式标注，并提示可改用字符区间手动校正，不静默给错位切片 |
| 标题区间对 PDF 全文无效（无 `#` 标记） | 该模式带"仅适用于含 `#` 标题的文档"提示；PDF 场景引导用默认的「按章节」；匹配不到时降级整篇并标注，不静默 |
| 无书签也无标题的文档，章节列表为空 | 自动切到「整篇」并提示；这是保留"整篇"模式的意义之一 |
| 子章节选中导致范围碎片化 | 勾选时父子联动 + 相邻选中段合并，展开文本按章节名列表标注 |
| 200KB 截断 | 展开文本显式声明截断；不静默 |
| 抽取文本有 OCR 噪声、丢表格公式 | 这是抽取全文的固有缺陷，不掩盖；引导用户配合截图 chip（图 + 文互补，已是现有能力） |
| 正文在提交时现取，草稿期间文库可能变化 | 与 `item:` 现取类同语义，已有 `isMissing()` 处理删除场景，行为一致 |
| 独立笔记重复 | 对 `itemType=note` 隐藏全文按钮，走 `note:` |
| 浮层压住 macOS 窗口拖拽区 | 挂 `data-window-drag-exclude`（铁律） |

## 6. 验收标准

1. 打开任一有全文索引的 PDF 条目（PDF 已打开、书签已上报），点「全文」→ 默认「按章节」勾选「3 Method」→ 插 chip → 发送，模型答复能引用该节的方法/数据细节，且展开文本头部标注章节名与页码。
2. 四种范围模式均正确切片，展开文本头部标注与实际内容一致：
   - 按章节（PDF 书签 `p:`，含父子联动、跨页合并）；
   - 按章节（快照/笔记标题 `o:`，按字符偏移）；
   - 整篇 `all`；
   - 字符区间 `c:`（边界 clamp 正确）；
   - 标题区间 `h:`（有 `#` 标题时切对；无匹配时降级整篇并标注）。
3. 默认打开选择器时「按章节」处于选中/置顶状态；整篇、字符、标题三种收在「更多方式」里，需展开才见。
4. 书签标题对不上文字层时，展开文本含"位置为估算"标注，且提示可改用字符区间。
5. 在设置里把 `mcp__zotero__*` 全部禁用，重复步骤 1，全文仍能进对话（验证"不依赖 MCP"）。
6. 超长全文发送，展开文本含截断声明。
7. 无全文索引的条目，按钮置灰并给出提示；独立笔记不出现全文按钮。
8. 全文 chip 的展开文本明确声明"不含图片/图表/公式"，配合截图 chip 使用时两者出处可对齐（见第 8 节）。
9. 历史记录里全文引用收成胶囊，不撑爆会话视图。
10. `pnpm typecheck:client` 通过；`tsdown`（clean:false）构建通过；刷新 webview 即可，Host 无需重启。

## 7. 分期建议

- **第一期（一次做完整，评审确认）**：`full:` 引用类型 + **4 模式范围选择器**（默认「按章节」复用 PDF 书签/文档标题；保留整篇 / 字符区间 / 标题区间）一次交付。章节选择不是增强项而是必需项。
- **第二期（可选，独立评估）**：整份 PDF 作为文件附件投喂模型（见第 9 节），与本文的全文文本方案是两条独立路线，需先验证模型侧文件输入的实际效果与成本。
- **第三期（可选）**：文献对比矩阵模板（选 N 篇 + 全文 → 结构化对比表），这是上一轮的全局建议，与本文独立。

## 8. 文字与图片的分流策略

### 8.1 根本事实：全文抽取里没有图片

`ZoteroFulltext`（`src/zotero/types.ts:304-310`）只有 `attachmentKey / content / truncated / fallback` 四个字段，`content` 是 Zotero 全文索引的**纯文本流**——图表、示意图、公式排版、表格、图标、照片全部不在其中。这是 Zotero 索引的固有形态，不是插件缺陷。所以『全文 chip』这条路送进模型的**永远只有文字**，不能也不该试图让它带图。

处理原则是**分流 + 互补**：文字靠全文文本读，图靠位图读（模型是多模态的，截图作为图片附件进去，能直接看懂曲线、表格、结构）。两条 chip 进同一条消息。

### 8.2 图片靠用户自行截图，走已有的 shot/ 能力

现有 `shot/` 已按文档类型做了 adapter，覆盖三种图片来源：

| 图片所在场景 | adapter | 能力 | 出处 |
|---|---|---|---|
| PDF 里的图表/公式/示意图 | `adapters/pdf.ts` | 直接读 pdf.js 画好的页 canvas，`drawImage` 无损拼接；**绕开文字层乱码**，图是什么样模型看到什么样 | 自动算印刷页码 + 最近书签章节，烧进水印 |
| 网页快照里的图 | `adapters/iframe.ts` / `dom.ts` | DOM 转图；快照 CSP 允许 `img-src data: blob:`，内嵌图能渲染 | 按标题元素纵向位置定章节 |
| 纯文本/Markdown 里的图 | `adapters/dom.ts` | html-to-image 抓渲染后 DOM | 按标题定位 |

用户操作：框选矩形 →「截图加入对话」→ 位图 + `shot:` 出处 chip 一起进消息；水印带「Zotero 截图 ·《标题》· P页码 · 章节」。

### 8.3 必须写进文案的边界

- **全文 chip 的展开文本显式声明"不含图片/图表/公式"**，避免用户误以为加入了全文就什么都拿到了，引导其对关键图表补截图。
- **截图像素上限** `MAX_SHOT_PIXELS = 16,000,000`（约 4000×4000，`shot/types.ts:139`），框选超大区域会等比缩小（`composer.ts` 的 `fit()`），数据密集的图表要框紧。
- **公式分两种**：PDF 文本层里可复制的公式 → 全文抽取会变乱码，截图是唯一可靠通道；纯图片公式 → 只能截图。
- **图文关联靠水印的页码/章节**：模型同时收到全文与截图后，靠水印把图对回正文段落——这是水印不只是署名的原因。
- **图标/小装饰图**：无信息量，忽略即可；真正要处理的是承载数据的图。

### 8.4 可选增强（不在第一期）

「整页截图」快捷按钮：当前要手动框选，若用户正在读某一页，一键把整页转位图更顺手。属体验优化，非必需。

## 9. 备选路线：整份 PDF 直接作为附件投喂模型

评审中提出『能否把整份 PDF 直接给大模型』。查证结论（2026-11-20）：**模型侧与宿主侧当前都具备条件，但这条路线与本方案的全文文本路径是两回事，建议单列第二期验证。**

### 9.1 可行性证据

**模型侧（DeepSeek V4.1-Flash）**：2026-11-13 DeepSeek 开放"全家桶应用 API"，V4.1-Flash（模型名 `deepseek-flash`，当前构建 `DeepSeek-V4.1-Flash-1017`）在 Messages / Responses / Chat Completions 三大接口下支持文件输入——上传 PDF / Office / 图片，服务端做纯文本提取或图文混排解析后拼入上下文；1M 上下文；独立 OCR 接口约 1.5 元/千页。（来源：澎湃新闻、新蓝网 2026-11-13 报道；llm.okamomedia.tokyo 模型页，2026-11-17 核验）

**宿主侧（本地 DSH 0.2.1-rc.5）**：`createDrafts(sessionId, files)` 的实现里，非图片文件明确创建 `kind: "file"` 附件并走 `beginFileUpload()`（`dsh-client-ui-conversation/lib/client.js:4751-4767`）；`@deepseek-ai/dsh-client-file-upload` 提供按 Session 寻址的流式文件上传与暂存凭证，**说明 DSH 本身支持传任意文件（含 PDF）作为对话附件**，不限于图片。

### 9.2 为什么仍建议先做全文文本方案

- **可控性**：全文文本方案按字符/标题切片，取哪段用户说了算，成本与上下文占用可预测；整份 PDF 投喂由服务端解析，切片粒度不可控，长文仍可能触及模型侧上限或解析质量波动。
- **出处链**：全文 chip 自带稳定 key + 页码/章节，与现有 citation 体系一脉相承；PDF 附件投喂后模型能否逐条给出可追溯出处，需实测。
- **确定性**：全文文本走面板自己的 `fetchItem()` HTTP 通道，与 MCP 开关无关；PDF 附件投喂依赖 DSH 把附件正确映射到 DeepSeek 文件输入参数——这条链路本地 rc.5 版本是否端到端打通，**尚无实跑证据**。
- **成本**：文件解析按页计费，叠加 token；全文文本方案复用已索引的文本，边际成本近零。

### 9.3 若要做，验证清单（第二期前置）

1. 本地 DSH rc.5 实跑：把一个 PDF 作为文件附件挂进对话并发送，确认模型确实读到了内容（而非只收到一个附件占位）。
2. 确认模型侧是否真的是 `deepseek-flash` 且会话所用部署已开启文件输入参数；换用其他模型时行为如何。
3. 测一份 100 页论文，看解析质量（图表、公式、双栏）与出处可追溯性，与全文文本方案对比。
4. 核对文件解析计费与 token 成本。

> 结论：PDF 附件投喂是值得跟进的方向，但属"模型/宿主能力驱动"的新路线，风险与成本都需实测；本期的确定性收益来自全文文本 + 范围选择器。
