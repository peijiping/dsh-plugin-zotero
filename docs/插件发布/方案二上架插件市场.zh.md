# 方案二：上架插件市场（awesome-dsh-plugin 收录流程）

> 适合正式对外发布，让别人从插件市场一键安装。
>
> 心智模型：**插件市场本身没有服务器端"投稿接口"，上架 = 往精选列表 [awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 提一个 PR，往里加一个 YAML 条目**。维护者 review + CI 绿 → 合并 → 上游构建生成 `plugins.json` / `index.json` → 市场每次读取。
>
> 本文是 `peijiping/dsh-plugin-zotero` 的实际操作记录，命令可直接复用。最近一次核对：**2026-10-19**（v0.1.2 已用 `pnpm publish` 直发 npm，等待当夜 probe 把 npm 字段写进市场数据）。

## 零、先回答两个问题

### 1. dsh 推荐 pnpm 吗？——是，但先分清"包管理器"和"分发渠道"

`dsh` 并不自己实现依赖管理：`dsh plugin --profile <name> <args...>` 会把参数**原样转发给 pnpm**（官方文档原文），profile 的 `package.json`、锁文件、`pnpm-workspace.yaml` 都由 pnpm 维护。所以"用 pnpm"是 dsh 的既定事实，不是偏好。

但 **npm 在这里指的是 registry（分发渠道），不是 npm CLI**。两者不冲突：

| 用途 | 用什么 | 说明 |
|---|---|---|
| 装依赖 / 构建 / 打包 / 发布包 | **pnpm** | 本仓库与 `tstest/` 统一 pnpm，锁文件 `lockfileVersion: 9.0`；npm/yarn 混装会反复重建 `node_modules` |
| 用户把插件装进 profile | `dsh plugin ... add <spec>` | 内部仍是 pnpm（桌面端自带 pnpm 11.28.5） |
| 包分发、版本号、下载量 | **npm registry** | `pnpm publish` 发布到的就是 registry.npmjs.org；`pnpm add dsh-plugin-zotero` 消费的也是它 |
| 官方「发现」页读取的版本 | registry 的 `dist-tags.latest` | 由上游 bot 探测，见第八节 |

结论：**发布用 `pnpm publish`，不要用 `npm publish`**。本仓库的 `prepack` 里也是 `pnpm build`，混用 npm CLI 只会多一条不受控的路径；而且 npm 11.14 对新包的首次发布会走 **staged publishing**，出现 `0.0.0-stage` 占位版本（本仓库 v0.1.0 就踩过）。pnpm ≥ 11.3 也支持 staged，但它是显式的 `pnpm stage publish`；普通 `pnpm publish` 是直接上线。

## 一、上架链路（先搞清楚顺序）

```
你的仓库（package.json 声明 dsh.bundle.patch）
   │
   ├─1─ 提 PR：data/plugins/<owner>__<repo>.yml        ← 只能改这一个文件
   │
   ├─2─ CI 跑绿（check = 表单校验；Submission gate = 语义核验）
   │
   ├─3─ 维护者 review + 合并                            ← 无法自助，只能等
   │
   ├─4─ 上游 "Build site from README" 重新生成
   │      ├─ plugins.json   旧版市场 / dsh-market 读取（含 npm、version、install）
   │      └─ index.json     dsh ≥ 0.2.1 官方「发现」页读取（format 1）
   │
   └─5─ 市场打开即拉取 → 能搜到
```

三个必须先记住的点：

| 点 | 说明 |
|---|---|
| README 是生成物 | 两个 README 由脚本从 `data/plugins/*.yml` 生成，**不要手工编辑 README** |
| npm 字段不是条目字段 | 条目里**禁止**写 `npm:`（未知字段会被校验拒绝）；npm 映射由 nightly probe 从仓库 `package.json` 与 registry 自动解析 |
| 收录 ≠ 可安装 | 收录只决定"能不能被搜到"；能否免授权安装取决于 `npm` 映射或 `tarball:` |

### 收录硬性条件核对（本次实测）

| 条件 | 要求 | 本次状态 |
|---|---|---|
| 仓库公开 | 必须 | ✅ |
| 仓库年龄 | 创建满 1 天以上 | ✅ 2026-10-08 创建 |
| manifest | `package.json` 声明 `dsh.bundle.patch` | ✅ |
| 真实代码 | 不是空壳仓库 | ✅ |
| 仓库 topic | 打 `dsh-plugin` | ✅（原缺，后补） |
| 描述属实 | 不得夸大、不得写"最好用" | ✅ |

## 二、发布前的一次性准备

### 1. package.json 补齐字段

当前有效字段（v0.1.2 起的形态）：

```json
{
  "name": "dsh-plugin-zotero",
  "version": "0.1.2",
  "description": "一句话英文说明（npm 与市场卡片会用到）",
  "keywords": ["dsh", "deepseek", "harness", "dsh-plugin", "zotero", "cordis", "mcp"],
  "license": "MIT",
  "repository": { "type": "git", "url": "git+https://github.com/peijiping/dsh-plugin-zotero.git" },
  "homepage": "https://github.com/peijiping/dsh-plugin-zotero#readme",
  "type": "module",
  "main": "lib/index.js",
  "types": "./lib/index.d.ts",
  "exports": {
    ".": { "types": "./lib/index.d.ts", "default": "./lib/index.js" },
    "./client": "./client/client.js"
  },
  "files": ["lib", "client", "cordis.patch.yml"],
  "engines": { "dsh": ">=0.2.0-rc.2 <0.3.0-0" },
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1",
    "@deepseek-ai/schemastery": "^3.18.4"
  },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": { "platform": "web", "inject": ["…"] }
  },
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "build:client": "tsdown",
    "prepack": "pnpm build && pnpm build:client"
  }
}
```

要点：

- `dsh.bundle.patch` 是收录 CI 唯一会检查的 manifest 字段，缺了直接被判不通过；只有 `dsh.client` **不算可安装**。
- **`prepack` 是关键**：没有它，`pnpm pack` / `pnpm publish` 不会自动构建，打出来的包里没有 `lib/`，别人装上直接加载失败。`prepack` 在 `pnpm pack`、`pnpm publish` 前都会跑，所以不必再手动构建一遍。
- `repository` 是 npm ↔ 仓库的关联依据：上游 probe 只有在仓库 `HEAD/package.json` 的 `name` 等于 npm 包名、**且包内 `repository` 回指同一仓库**（大小写不敏感）时才采纳，防抢注。
- `engines.dsh` 建议声明。官方「发现」页用它计算兼容性并选默认版本；安装前 `dsh` 也会先校验它（不满足时**在 pnpm 运行前**失败，不会下载任何东西）。条目里有它之后，`workspace:` 范围或 `@deepseek-ai/dsh-*` peer 不再参与判断。
- `peerDependencies` 放"要与宿主共享实例的 dsh 包"（本插件是 `cordis` 与 `schemastery`），并**同时放进 devDependencies**；devDependency 副本供类型检查与独立测试。无状态工具包或需要独立版本的第三方依赖才放 `dependencies`。
- `types` 可省，但加上之后 TS 使用者无需猜 `lib/index.d.ts`。
- `files` 里不要写不存在的目录（本仓库曾有 `locale`，但文案其实打包在 `client/client.js` 里）。

## 三、构建与打包

```sh
cd /Users/peijiping/Documents/Codes/TS/dsh-plugin-zotero

pnpm typecheck:client  # 可选：客户端类型校验
pnpm pack              # 触发 prepack（build + build:client），产出 dsh-plugin-zotero-<version>.tgz

# 核对产物清单（务必做，比"构建成功"四个字更有说服力）

```

预期清单（缺任何一个都会导致安装失败）：

```
package/package.json
package/README.md
package/LICENSE
package/cordis.patch.yml          ← 没有它 dsh 不认这是 bundle
package/lib/index.js 等           ← main / exports 的落地文件
package/lib/index.d.ts            ← types 指向的文件
package/client/client.js          ← client 注入产物
```

**做一次真实加载测试**（比 `--dump-config` 更有说服力：`--dump-config` 只组合 YAML，不 import 模块）：

```sh
DSH_HOME=/tmp/dsh-pack-test dsh plugin --profile test add ./dsh-plugin-zotero-0.1.2.tgz
DSH_HOME=/tmp/dsh-pack-test dsh --profile test --dump-config-schema | grep -c dsh-plugin-zotero
# 退出码 0 且计数 ≥1，说明宿主真的 import 了包、读到了它的 Config Schema
```

这能提前抓出"依赖没声明、运行时 `MODULE_NOT_FOUND`"这类只在安装后才暴露的问题。

## 四、发 npm（主路径）

v0.1.1 起 npm 是**主产物**：市场安装命令优先 npm，官方「发现」页也只收录能解析到 npm 的条目。

```sh
# 1. 改版本并提交（如 0.1.2）
# 2. 发布（prepack 自动构建；--access public 对无 scope 包可省）
pnpm publish --access public
```

前置条件：npm 账号已注册、**邮箱已验证**。开了 2FA 时 `pnpm publish` 会要 OTP，可在 npm 网页建 granular access token（`All packages` + `Read and write` + bypass 2FA）写入 `~/.npmrc` 后免交互。**恢复码不能用于 `--otp`。**

发布后立刻核对 registry（不要只看"发布成功"）：

```sh
npm view dsh-plugin-zotero version dist-tags --json
# 或直接读 JSON（npm CLI 缓存异常时也能用）
curl -s https://registry.npmjs.org/dsh-plugin-zotero | python3 -c "
import json,sys
d=json.load(sys.stdin)
print('latest', d['dist-tags']['latest'])
print('versions', list(d['versions']))
print('published', d['time'][d['dist-tags']['latest']])
"
```

### 发布后立即安装可能报 404（registry CDN 缓存）

刚发布完的几分钟内，元数据接口已经能看到新版本，但 tarball URL 可能仍返回 404：

```
GET https://registry.npmjs.org/dsh-plugin-zotero/-/dsh-plugin-zotero-0.1.2.tgz → 404
cache-control: public, max-age=300
```

这是 Cloudflare 在发布瞬间把 404 缓存了 5 分钟，不是发布失败。`pnpm add` / `dsh plugin add` 不会加 cache-buster，所以会直接失败。**等 5 分钟再装**；急着验证时给 tarball URL 加 `?cb=$(date +%s)`（只用于 curl 下载）。

### 关于 staged publishing（v0.1.0 踩过）

npm 11.14 对新包的首次发布会进 **暂存队列**，registry 里只出现占位版本 `0.0.0-stage`（`description` 为 `Temporary package placeholder for staged publishing`），真实版本在批准前**不可安装**，`dist-tags.latest` 仍指向占位符。别误判成"发成功了"。

- 用 **`pnpm publish`** 走的是 pnpm 自己的发布实现，不经过 npm 的暂存流程（本项目 v0.1.1 已确认直接上线）。
- 若仍拿到 stage：npm 网页 → 头像菜单 → **Staged Packages** → Approve；或 pnpm ≥ 11.3：`pnpm stage list` / `pnpm stage view <stage-id>` / `pnpm stage approve <stage-id>`（11.14 及以下的 npm CLI 没有 `stage` 子命令）。
- 放行后 `versions` 才会出现真实版本，`latest` 随之切换。

## 五、发 GitHub Release（可选，兜底用）

**这一步不再是必须的。** 上游生成安装命令的优先级是：

```
npm 已映射  →  dsh plugin --profile web add <npm 包名>
否则有 tarball →  dsh plugin --profile web add "<tarball URL>"
否则          →  dsh plugin --profile web add github:owner/repo
```

所以 npm 一旦被 probe 收录，`tarball:` 只作为 npm 不可用时的兜底（也是 npm 映射生效前那段时间的兜底）。仍建议保留一个 Release，原因只有两个：npm 映射前的窗口期，以及 registry/镜像不可达时的备用下载。**tarball 与 npm 包都是预构建产物，用户都不需要 `allowBuilds` 授权；只有 `github:` 源码安装才需要。**

资产名**不带版本号**：`dsh-plugin-zotero.tgz`。这样 `releases/latest/download/` 永久链接不会随版本失效，条目文件也不用每次改。

网页端：Releases → Draft a new release → 新 tag（如 `v0.1.2`）→ 上传 `dsh-plugin-zotero-0.1.2.tgz` → **把上传后的资产重命名**为 `dsh-plugin-zotero.tgz` → Publish release。

API 方式（两条命令：建 Release + 传资产）：

```sh
# 建 release（注意：不要传 target_commitish！传短 SHA 会直接 422）
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://api.github.com/repos/peijiping/dsh-plugin-zotero/releases \
  -d '{"tag_name":"v0.1.2","name":"v0.1.2","body":"发布说明","draft":false,"prerelease":false}'

# 取 release id
RID=$(curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/peijiping/dsh-plugin-zotero/releases/tags/v0.1.2 \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['id'])")

# 上传资产（走 uploads.github.com，不是 api.github.com）
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/gzip' \
  --data-binary @dsh-plugin-zotero-0.1.2.tgz \
  "https://uploads.github.com/repos/peijiping/dsh-plugin-zotero/releases/$RID/assets?name=dsh-plugin-zotero.tgz"
```

## 六、提交收录 PR

只加**一个文件**：`data/plugins/<owner>__<repo>.yml`（一个插件一个 YAML，文件名用双下划线分隔 owner 与 repo）。

本次已合并的内容：

```yaml
url: https://github.com/peijiping/dsh-plugin-zotero
name: peijiping/dsh-plugin-zotero
category: tools
tarball: https://github.com/peijiping/dsh-plugin-zotero/releases/latest/download/dsh-plugin-zotero.tgz
description:
  en: '一句话英文描述，以句号结尾。'
  zh: 一句话中文描述，以句号结尾。
```

| 字段 | 要求 |
|---|---|
| `url` | 必须与仓库地址完全一致（不要多余斜杠） |
| `name` | 列表里显示的链接文字，用 `owner/repo` |
| `category` | 必须取自上游分类表（`tools`、`ui`、`dev` 等），选不准维护者会改 |
| `tarball` | 可选。必须是 **GitHub 自家 Release 托管**的 https `.tgz`；有 npm 映射时安装命令不会用它 |
| `description.en` | **唯一必填**，一句话、以句号结尾、不夸张；含 `: ` 时必须加引号 |
| `description.zh` | 可留空，维护者会补；能写就写上 |
| `npm` / `version` | **禁止手写**。上游 `ENTRY_KEYS` 只允许 `url`、`name`、`category`、`description`、`tarball`，多写会被 CI 拒绝；npm 映射由 bot 探测 |

命令版流程（fork → 分支 → 写文件 → 开 PR）：

```sh
UP=awesome-dsh-plugin/awesome-dsh-plugin
FILE=data/plugins/peijiping__dsh-plugin-zotero.yml
BR=add-dsh-plugin-zotero

# 1. fork（已 fork 过会报已存在，可忽略）
curl -s -X POST -H "Authorization: Bearer $TOKEN" https://api.github.com/repos/$UP/forks

# 2. 从 fork 的默认分支建一个工作分支
SHA=$(curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/ref/heads/main \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['object']['sha'])")

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/refs \
  -d "{\"ref\":\"refs/heads/$BR\",\"sha\":\"$SHA\"}"

# 3. 提交条目文件（content 必须是 base64）
CONTENT=$(base64 -i entry.yml | tr -d '\n')
curl -s -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  "https://api.github.com/repos/peijiping/awesome-dsh-plugin/contents/$FILE" \
  -d "{\"message\":\"Add peijiping/dsh-plugin-zotero\",\"branch\":\"$BR\",\"content\":\"$CONTENT\"}"

# 4. 开 PR（head 写成 owner:branch，base 是上游默认分支）
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://api.github.com/repos/$UP/pulls \
  -d "{\"title\":\"Add peijiping/dsh-plugin-zotero\",\"head\":\"peijiping:$BR\",\"base\":\"main\",\"body\":\"PR 说明\"}"
```

网页端等价做法：fork → 在 fork 里 Add file → 提 PR 到上游 `main`。

## 七、怎么检查是否提交成功（五级检查，从早到晚）

五级是递进的，**后一级通过不代表前一级可以跳过**；排障时按顺序逐级看。

| 级别 | 检查什么 | 通过判据 |
|---|---|---|
| L1 | PR 本身的状态 | `state=open` 且零冲突 |
| L2 | CI 两个检查项 | `check=success` 且 `Submission gate=success` |
| L3 | 条目文件是否进了上游仓库 | HTTP `200`（`404` = 还没合并） |
| L4 | `plugins.json` 是否收录 + npm 映射 | 能 grep 到仓库；`npm` / `version` 非 null；`install` 以 `dsh plugin ... add dsh-plugin-zotero` 开头 |
| L5 | `index.json`（官方「发现」）是否收录 | 条目带 `versions[0].version` 与 `publishTimestamp` |

### 准备：取 token 与变量

```sh
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
UP=awesome-dsh-plugin/awesome-dsh-plugin
PR=7644
```

### L1 看 PR 状态

```sh
curl -s -H "Authorization: Bearer $TOKEN" https://api.github.com/repos/$UP/pulls/$PR \
  | python3 -c "import json,sys;d=json.load(sys.stdin);print('state',d['state'],'| merged',bool(d['merged_at']),'| merged_at',d['merged_at'],'| mergeable',d['mergeable'])"
```

- `merged True` → 已收录，去做 L4。
- `state open` + `mergeable True` → 正常排队，看 L2。
- `mergeable None` → GitHub 还在算，过一会儿再看。

### L2 看 CI 两个检查项

```sh
SHA=$(curl -s -H "Authorization: Bearer $TOKEN" https://api.github.com/repos/$UP/pulls/$PR \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['head']['sha'])")

curl -s -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/repos/$UP/commits/$SHA/check-runs" \
  | python3 -c "import json,sys;[print(c['name'],'|',c['status'],'|',c['conclusion']) for c in json.load(sys.stdin)['check_runs']]"
```

判读表——**这里是最容易误判的地方**：

| 结论 | 含义 | 该做什么 |
|---|---|---|
| `check: success` | 表单校验过（YAML 合法、只加一个文件、路径规范） | 继续看 gate |
| `Submission gate: success` | 语义核验过（`dsh.bundle` 存在、仓库满 1 天） | 具备合并条件，等维护者 |
| `Submission gate: neutral` | **并未核验**，多半是对方机器人撞了 GitHub API 限流（403） | ⚠️ 维护者只会合 gate = success 的 PR，neutral 会被静默跳过 → 见下"重触发" |
| `Submission gate: failure` | 真有问题，看它附的说明 | 按说明改条目或改仓库 |
| `Repository config guard: failure` | 不阻塞合并（实测有带 failure 仍被合并的 PR） | 看一眼即可 |

**看 gate 的细节文字**（含 `neutral` 的具体原因）：

```sh
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/repos/$UP/commits/$SHA/check-runs" \
  | python3 -c "import json,sys;[print(c['name'],'->',(c.get('output') or {}).get('summary','')) for c in json.load(sys.stdin)['check_runs']]"
```

**gate 卡在 `neutral` 的解法**——往 PR 分支推一个空提交，重新触发 PR 同步事件（限流按小时重置，隔一段时间再做）：

```sh
HEAD=$(curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/ref/heads/add-dsh-plugin-zotero \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['object']['sha'])")
TREE=$(curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/commits/$HEAD \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['tree']['sha'])")

NEW=$(curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/commits \
  -d "{\"message\":\"chore: re-trigger CI\",\"tree\":\"$TREE\",\"parents\":[\"$HEAD\"]}" \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['sha'])")

curl -s -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://api.github.com/repos/peijiping/awesome-dsh-plugin/git/refs/heads/add-dsh-plugin-zotero \
  -d "{\"sha\":\"$NEW\"}"
```

### L3 看条目文件是否进了上游（合并的硬标志）

```sh
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/$UP/contents/$FILE
```

`HTTP 200` = 已合并（收录通过）；`HTTP 404` = 还没合并。

### L4 看 `plugins.json`（旧市场 / dsh-market）

`https://awesome-dsh-plugin.com/plugins.json` 在本机**时好时坏**（可能超时，也可能 200 但响应体被截断）。`grep` 返回 0 不等于未收录，**以 npm 上的 `dsh-plugin-catalog` 为准**：上游每次 nightly 会把同一份 `plugins.json` 和 `index.json` 一起发布到该包。

```sh
cd /tmp
curl -s https://registry.npmjs.org/dsh-plugin-catalog/latest \
  | python3 -c 'import json,sys;print(json.load(sys.stdin)["dist"]["tarball"])' \
  | xargs curl -sL -o catalog.tgz
tar -xzOf catalog.tgz package/plugins.json > plugins.json
tar -xzOf catalog.tgz package/index.json > index.json

python3 - <<'EOF'
import json
d=json.load(open('/tmp/plugins.json'))
hits=[p for p in d['plugins'] if p.get('url')=='https://github.com/peijiping/dsh-plugin-zotero']
print('plugins.json hits', len(hits))
for h in hits:
    print({k:h.get(k) for k in ('name','npm','version','install','tarball')})
EOF
```

判据：

- `npm` 为 `null` → probe 还没跑到（或 npm 包不满足 `name`/`repository` 回指条件）。等下一轮 nightly。
- `npm` 非 `null` → `install` 应变成 `dsh plugin --profile web add dsh-plugin-zotero`；`version` 等于 registry 的 `latest`。
- 注意 `plugins.json` 顶层的 `updated` 是"最近新增条目的日期"，**不是构建时间**。判断新鲜度要看 catalog 包的版本号/发布时间（`dsh-plugin-catalog@2026.1019.8082` 发布于 2026-10-19T04:11Z）。

### L5 看 `index.json`（官方「发现」页）

dsh ≥ 0.2.1 的「插件 → 发现」读取的是 **format 1** 的市场索引，和 `plugins.json` 是两份数据。它只收录同时具备 **npm 包名 + 精确版本 + 该版本发布时间** 的条目；`engines.dsh` 可选，但有它才会显示兼容性并按版本过滤。

```sh
python3 - <<'EOF'
import json
d=json.load(open('/tmp/index.json'))
print('format', d.get('format'), '| plugins', len(d['plugins']))
hits=[p for p in d['plugins'] if p.get('repository',{}).get('url','').endswith('dsh-plugin-zotero')]
print('index.json hits', len(hits))
for h in hits: print(json.dumps(h, ensure_ascii=False, indent=2))
EOF
```

`hits >= 1` 说明官方「发现」页能搜到；`0` 且 L4 的 `npm` 仍为 `null`，就是同一原因：等 nightly。

> 「发现」页需要用户自己添加索引源：**插件 → 发现 → 添加索引源 → `https://awesome-dsh-plugin.com/index.json`**。上游明确"目前没有官方插件市场"，索引源由用户配置。

### 附加：上游构建任务是否在跑

## 八、以后发新版本（npm 主路径）

发版主路径只有一件事：**发 npm**。GitHub Release 是可选的兜底。

```sh
# 1. 改 version（如 0.1.3）并提交
# 2. 构建 + 打包 + 发布 —— prepack 会自动跑 build 与 build:client
pnpm pack                       # 可选：本地核对产物
pnpm publish --access public    # 需 npm 登录；开了 2FA 会提示 OTP
# 3. 可选：建新 Release（如 v0.1.3），资产仍命名为 dsh-plugin-zotero.tgz
# 4. 等 nightly（02:23 UTC / 10:23 北京）或上游其它构建；作者无法手动 dispatch
```

两步各自的影响（**与旧文档不同，注意这里**）：

| 步骤 | 不做的后果 |
|---|---|
| `pnpm publish` | 市场拿不到 `npm` / `version`：`install` 只能回落到 `tarball`（或 `github:`），`index.json` 不收，客户端检测不到新版本 |
| GitHub Release | **npm 已映射时不影响安装**；只影响 npm 不可达时的兜底，以及 npm 映射生效前的窗口期 |

发 npm 后上游 bot（`scripts/probe-npm.mjs`）会自动填字段，采纳条件是：

1. 仓库 `HEAD/package.json` 的 `name` 等于 npm 包名；
2. registry 里存在该包；
3. 该包 **`latest` 版本的 `repository`** 回指同一 GitHub 仓库（大小写不敏感，`git+https://…git` 也算）。

本仓库三条都满足，`npm` / `version` 无需人工干预。

条目文件**不用动**：`latest/download/dsh-plugin-zotero.tgz` 会自动指向最新且资产名匹配的 Release；`npm` / `version` / `publishedAt` / `enginesDsh` 全由 bot 探测填充。

只有这两件事需要重新提 PR：**改条目描述/分类**，或**仓库改名/迁移**。

### npm 字段多久生效（我们能做的到此为止）

上游对 npm 的探测由 bot 完成，**作者无法手动触发**：`workflow_dispatch` 需要该仓库的 admin 权限，而我们从 fork 提 PR 只得到 `pull`（实测 `POST /actions/workflows/build-site.yml/dispatches` → `403 Must have admin rights to Repository`）；push 构建又明确不探测（`build-site.yml`：Push builds deploy but do NOT probe）。

所以只能等 nightly（`cron '23 2 * * *'` = 北京时间 10:23）：

- nightly 以 `PROBE_ALL=1` 全量重探；`npm: null` 的判定满一天（`RECHECK_DAYS = 1`）也会重探，所以**次日 nightly 通常能把 `npm` / `version` 补上**。
- probe 数据 `data/npm-map.json` 只存在于 Actions cache（仓库里没有这个文件），所以**不要用"GitHub 上搜不到 npm-map.json"判断 probe 失败**。
- 该 nightly 也是把 catalog 发布到 npm（`dsh-plugin-catalog`）的 run —— 用 catalog 校验时，字段生效时间与站点同步，都在次日 nightly 之后。
- 如果次日仍为 `null`：先看 L4 的 package 时间戳是否真的更新；再核对第 3 条采纳条件（尤其 `repository` 是否指向带 `.git` 的同一仓库）。

验证动作：nightly 后重跑第七节 L4/L5，确认 `npm` 等于 `dsh-plugin-zotero`、`version` 为最新版本号、`install` 变成 `dsh plugin --profile web add dsh-plugin-zotero`，且 `index.json` 出现该条目。

## 九、踩坑记录（本次实测）

| 坑 | 现象 | 解法 |
|---|---|---|
| 本机 `git push` 超时 | `Recv failure: Operation timed out`；但 `api.github.com` 一直正常 | 重试 2~3 次；持续失败就改用 REST API 提交 |
| 直接被拒推 | `remote contains work that you do not have locally` | `git fetch origin` 后 `git rebase origin/main` 再推。**注意**：变基会把远端已删掉的文件从本地磁盘一并删掉，先 `cp -R` 备份再变基 |
| `Submission gate: neutral` | 自己查 L2 是 neutral，但同批别家 PR 已合并 | 对方机器人限流未核验，不是你的问题。按第七节"重触发"推空提交重跑 |
| 发布 API 报 422 | `tag_name is not a valid tag` | 别传 `target_commitish`（短 SHA 会触发校验失败），省略即取默认分支 HEAD |
| 市场里搜不到 | 市场无条目 | 依次看 L3/L4/L5：没合并 → 等维护者；合并了但没命中 → 等 nightly probe |
| 漏打 topic | 收录条件不满足 | 见第二节第 3 步；API 是覆盖式写入，要一次列全 |
| `pnpm pack` 产物缺 `lib/` | 别人装上报找不到入口 | 加 `prepack` 脚本 |
| `locale/` 在 `files` 里但不存在 | 产物体检时误以为缺文件 | 从 `files` 删除；文案实际在 `client/client.js` 里 |
| npm CLI 报 `EPERM ... _cacache` / "root-owned files" | 沙箱或缓存目录权限问题，读命令也会失败 | 优先用 pnpm（独立 store）；必须用 npm 时 `npm --cache /tmp/npm-cache ...`，或修 `~/.npm` 属主 |
| `raw.githubusercontent.com` 访问不了 | 拉 README / package.json 失败 | 换 `api.github.com` 的 contents 接口 |
| npm 发布报 `ENEEDAUTH` | 本机未登录 npm | `npm login`（推荐 `--auth-type=web`）或写入 granular token |
| npm 发布报 `E403 ... Two-factor authentication or granular access token with bypass 2fa enabled is required` | 登录令牌不具备免 OTP 发布权限 | 终端输 authenticator 的 6 位动态码（或 `--otp <code>`）；**恢复码不能用于 `--otp`** |
| npm 发布报 `E403 ... verify your email` | 邮箱未验证 | 去邮箱点验证链接 |
| registry 只有 `0.0.0-stage` | **npm staged publishing**：新包首发布进暂存队列，真实版本批准前不可安装 | 用 `pnpm publish` 直接发布；或 npm 网页 → Staged Packages → Approve，或 `pnpm stage approve <stage-id>`（pnpm ≥ 11.3） |
| `pnpm publish` 报 `ERR_PNPM_OTP_NON_INTERACTIVE` | 非交互终端无法输入 2FA 动态码 | 在交互终端执行；或建 bypass 2FA 的 granular token |
| 发布后立刻安装报 `404 .../<version>.tgz` | registry CDN 缓存了发布瞬间的 404（`max-age=300`） | 等 5 分钟；curl 验证时给 tarball URL 加 `?cb=$(date +%s)` |
| L4 的 `grep` 恒为 `0` | `awesome-dsh-plugin.com` 超时或响应体截断，是假阴性 | 改从 npm 包 `dsh-plugin-catalog` 取 `plugins.json` / `index.json` |
| 条目写了 `npm:` 被 CI 拒 | `unknown field "npm"` | 删掉；npm 映射只能由 probe 自动生成 |
| 官方「发现」搜不到 | `index.json` 没有条目 | 该索引要求 npm 包名 + 精确版本 + 发布时间；npm 未映射就不会收 |

## 十、本次未走的备选路（留档）

- **只发 tarball、不发 npm**：能让用户免 `allowBuilds` 授权安装，但 `plugins.json` 里 `npm`/`version` 恒为 `null`，客户端检测不到更新，官方「发现」页也收不到。**v0.1.1 起已改为 npm 主路径**。
- **`screenshots.json`**：想在市场卡片里显示 App Store 式截图，可在仓库根放 `screenshots.json`（引用 1~8 张 GitHub 托管图片），下次构建自动生效——不用改 `data/plugins` 里的条目。
- **`github:` 源码安装**：不需要发布任何产物，但用户必须为 `prepare` 构建授权（`allowBuilds`），且构建脚本会在用户机器上执行。本插件不提供 `prepare`，**不要**把市场命令指向 `github:`。
