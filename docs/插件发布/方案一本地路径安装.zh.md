# 方案一：本地路径安装插件（操作参考）

> 适合开发阶段边写边测。原文档见 [basic-publish.zh.md](../DSH插件开发文档/basic-publish.zh.md) 与其 AI 讲解版 [basic_publish_ai.zh.md](../DSH插件开发文档/basic_publish_ai.zh.md)。
>
> 心智模型：**方式一 = pnpm 把你的插件目录 link 进 profile 的 `node_modules`，patch 只负责往 cordis 配置里插一行"按包名加载该包的 main 入口"**。整条链路是：包名 → `package.json` 的 `main` → 可加载的编译产物。

## 一、目录结构要求（打包三件套）

```
plugin_helloword/
├── package.json        # 声明 dsh.bundle，main 指向编译产物
├── tsconfig.json       # 编译 src/ -> lib/
├── cordis.patch.yml    # patch 层（声明要插入的插件行）
├── src/                # TypeScript 源码
│   ├── index.ts        # 入口（可选，见下文"入口两种写法"）
│   └── my-plugin.ts    # 插件/工具实现
└── lib/                # 构建产物（pnpm build 生成，勿手改）
```

## 二、三个关键文件的要求

### 1. package.json

```json
{
  "name": "plugin-helloword",
  "version": "1.0.0",
  "type": "module",
  "main": "lib/index.js",
  "files": ["lib", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
  "scripts": {
    "build": "tsc -p tsconfig.json"
  },
  "devDependencies": {
    "typescript": "^5.9.0"
  },
  "dependencies": {
    "@deepseek-ai/cordis": "^4.0.4",
    "@deepseek-ai/dsh-tools": "0.2.0-rc.2",
    "@deepseek-ai/schemastery": "3.18.4"
  }
}
```

逐项说明：

| 字段 | 要求 | 说明 |
|---|---|---|
| `name` | **必填**，须与 `cordis.patch.yml` 里的 `name` 完全一致 | cordis 按包名解析插件，两边对不上就找不到模块 |
| `type` | `"module"` | 插件主包均为 ESM |
| `main` | 指向一个**真实存在**的编译产物 | 这是"包名 → 入口"链路的最后一环 |
| `dsh.bundle.patch` | **必填**，指向 patch 文件 | 没有它 `dsh plugin add` 不识别为 bundle |
| `dependencies` | 源码里 import 的包都要登记 | 版本不能写占位符；可用 `npm view <pkg> versions` 查真实版本 |
| `files` | 发布清单 | 方式一本地 link 时不起作用，发布 npm 时生效 |

### 2. tsconfig.json

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "lib",
    "strict": true,
    "declaration": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

要点：

- `main` 指向的是 **JS 产物**，TS 源码必须先 `tsc` 转译，所以 `pnpm build` 是安装前的必做步骤。
- NodeNext 解析下，TS 源码里的相对引用要带 `.js` 后缀（如 `export * from './my-tool.js'`）。
- tsc 只编译存在的文件：`src/` 里没有 `index.ts`，`lib/` 里就不会有 `index.js`。

### 3. cordis.patch.yml

```yaml
- insert:
    - id: hello
      name: plugin-helloword        # 写包名，不是源码路径！
      config:
        greeting: 'Hi there!'
```

要点：

- `name` **按包名引用**（与 `package.json` 的 `name` 一致），不要写 `src/xxx.ts` 的绝对路径——那是 `dsh web --patch` 直接应用 patch 的开发玩法，和 `plugin add` 流程不兼容。
- `config` 的键必须与该插件 `Config` schema 的字段对应。
- patch 替换目标行的整个 `config` 值（不做深度合并）；后应用的层按行胜出。

## 三、入口两种写法

| 写法 | 做法 | 适用 |
|---|---|---|
| main 直指具体文件 | `"main": "lib/my-plugin.js"`，不需要 index.ts | 包内只暴露一个插件 |
| 独立入口文件 | `main` 指向 `lib/index.js`，`src/index.ts` 里 re-export | 一个包暴露多个模块，或想解耦文件名 |

独立入口的 `src/index.ts`：

```ts
export * from './my-plugin.js'   // 只导出要暴露的插件
```

## 四、操作步骤

```sh
cd /Users/peijiping/Documents/Codes/TS/dsh-plugin-zotero/plugin_helloword

# 0. 前置：确保 dsh 命令可用
#    桌面 App 的 dsh 在 /usr/local/bin/dsh；或装成 devDependency 后用 pnpm dsh

# 1. 安装依赖 + 构建
pnpm install
pnpm build

# 2. 本地路径安装进 profile（首次会自动初始化 profile）
dsh plugin --profile demo add ./

# 3. 验证 patch 层生效（输出中应看到该包对应的层）
dsh --profile demo --dump-config

# 4. 启动
dsh --profile demo
```

日常迭代：改 `src/` → `pnpm build` → 重启 `dsh`。link 的好处是**不需要重新 add**，编译产物更新后下次启动即生效。

卸载：

```sh
dsh plugin --profile demo remove plugin-helloword
```

## 五、踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| 缺 `dsh.bundle` 字段 | `dsh plugin add` 不识别为 bundle | package.json 补上 `"dsh": { "bundle": { "patch": "./..." } }` |
| patch 写源码绝对路径 | add 后模块解析失败 | patch 的 `name` 改写包名 |
| 依赖版本写占位符 `"..."` | pnpm install 直接报错 | 换成真实版本号 |
| `main` 指向不存在的文件 | 加载时找不到入口 | 先 `pnpm build`，确认 `lib/` 里有对应文件 |
| patch 名与包名不一致（如连字符 vs 下划线） | 按包名解析不到模块 | 两边保持完全一致 |
| esbuild 报 ERR_PNPM_IGNORED_BUILDS | 原生二进制没装上 | `pnpm-workspace.yaml` 加 `allowBuilds: { esbuild: true }` 后重新 install |
