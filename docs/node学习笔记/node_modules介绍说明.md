# node_modules 介绍说明

> `node_modules` 是包管理器（npm / pnpm / yarn）把依赖**真正下载到磁盘上的落地目录**。它不是临时缓存，而是"可随时重建的安装产物"。本文结合本项目里的 `tstest/node_modules` 讲解。

## 1. 它是干什么的

一句话：**`package.json` 是购物清单，`node_modules` 是买回来的实物。**

| 文件 / 目录 | 角色 |
|------------|------|
| `package.json` | 声明"我要哪些包、什么版本范围" |
| `package-lock.json` / `pnpm-lock.yaml` | 锁定"实际装到的确切版本" |
| `node_modules/` | 真正存放这些包的代码 |

没有它，`import` 会直接报 `Cannot find module`。

## 2. 目录长什么样

以 `tstest/node_modules` 为例：

```text
tstest/node_modules/
├── .bin/                     # 可执行命令的软链接（tsx、tsc 等）
├── .package-lock.json        # npm 记录的真实安装结果
├── tsx/                      # 普通包
├── typescript/
├── esbuild/
└── @esbuild/                 # 分包（scoped package），目录名带 @
    └── darwin-arm64/
```

几个要点：

- **目录名 = 包名**。`@scope/name` 这种带 `@` 的包会多一层目录。
- **`.bin/`** 存放可执行入口，`npx tsx`、`npm run` 时脚本能直接调用，靠的就是它。
- **`.package-lock.json`** 是安装结果的快照，不要手改。
- 层级有两种风格：npm 传统是**嵌套**（每个包自带一套依赖），npm 3+ 与 pnpm 会尽量**扁平化 / 用软链接复用**，避免同一份包存很多遍。

## 3. 核心机制：Node 如何找到包

当你写下 `import "tsx"` 时，Node 会从**当前文件所在目录**开始，逐级向上查找 `node_modules`，**第一个命中的就用**：

```text
tstest/src/main.ts  →  找 tstest/src/node_modules/tsx     ✗ 没有
                    →  找 tstest/node_modules/tsx          ✓ 命中，停止
                    →  （不会再去找）dsh-plugin-zotero/node_modules/tsx
                    →  （不会再去找）上一级目录……
```

这个规则带来两个重要推论：

1. **谁离得近谁生效**：同名包在子目录里存在时，会遮盖上层那份。
2. **子目录自己有一份 `node_modules`，就等于划出了独立的依赖边界**——这正是本项目 `tstest/` 能与主包环境隔离的原因。

## 4. 什么时候产生、什么时候更新

- **产生**：执行一次 `npm install` / `pnpm install` / `yarn` 时创建。
- **更新**：再次 `install`、`npm install 新包`、切换分支后 `install` 时增量变化。
- **不会自己产生**：只在编辑器里改代码、只写 `package.json`，都不会生成它。

安装过程中 npm 会同时更新锁文件，所以 `package.json`（声明）和锁文件（实际）要一起提交，`node_modules` 则不提交。

## 5. 是临时目录吗

**不是**，但要区分两个概念：

| | 可重建 | 是否算"临时" | 是否提交到 Git |
|---|---|---|---|
| `node_modules/` | ✅ 删掉重装即可恢复 | ❌ 属于安装产物 | ❌ 忽略 |
| `.cache/`、`*.tmp` | ✅ | ✅ | ❌ 忽略 |
| `lib/`、`dist/` | ✅ 重新构建 | ❌ 属于构建产物 | ❌ 忽略 |

判断标准是"**能否由源码 + 清单确定性地重建**"。`node_modules` 能（靠锁文件），所以进 `.gitignore`；但它体积大、内容是要被真正加载执行的代码，不是用完即弃的临时文件。

本项目根目录 [.gitignore](file:///Users/peijiping/Documents/Codes/TS/dsh-plugin-zotero/.gitignore) 已经忽略：

```gitignore
# 依赖
node_modules/

# 测试沙盒
tstest/node_modules/
```

## 6. 为什么本项目里会有多份 node_modules

因为 `node_modules` **跟着 `package.json` 走**：哪个目录有清单且装过依赖，哪个目录就有一份。本项目实际存在两处：

```text
dsh-plugin-zotero/            ← 主包：目前没有 node_modules（尚未 install）
└── tstest/
    └── node_modules/         ← 沙盒包：tsx、typescript 等装在这里

~/.dsh/profiles/desktop/
└── node_modules/             ← DSH profile：dsh-context、dshmarket 等装在这里
```

关于 `~/.dsh/profiles/desktop/node_modules`：

- 该目录本身就是一个包安装根，有 `package.json`（包名 `dsh-profile-desktop`，依赖 `dsh-context`、`dshmarket`）、`pnpm-lock.yaml` 和 `pnpm-workspace.yaml`（`packages: [.]`、`nodeLinker: hoisted`）。
- `package.json` 的 `dsh.profile.bundles` 列出 `dsh-base`、`dsh-web-app`、`dshmarket`、`dsh-context`，这些 bundle 需要真实代码才能加载。
- 本质上它和 `tstest/node_modules` 是同一种东西，只是由 DSH 在安装/更新 profile 时自动生成，不需要手动 `pnpm install`。

> 补充：主包之所以能直接用 `@deepseek-ai/cordis` 而不装一份，是因为它声明在 `peerDependencies` 里，由宿主 DSH 环境提供——插件与宿主必须共享同一份核心库实例。

## 7. 常用命令

```bash
npm install              # 按 package.json 安装，生成/更新 node_modules
npm ci                   # 严格按锁文件重装（先删旧的），CI 环境推荐
npm ls typescript        # 查看实际装到的版本
npm ls --depth=0         # 只看顶层依赖
npm prune                # 删除清单里已不存在的多余包
npm dedupe               # 尝试合并重复的嵌套依赖
rm -rf node_modules && npm install   # 万能重置大法
```

- **不要手改 `node_modules` 里的文件**：下次 `install` 会被覆盖，且无法追踪。
- 文件出问题（版本错乱、报模块找不到）时，**删掉重装**比逐层排查快得多。

## 8. 常见疑问

**Q：为什么它这么大？**
每个包会带上自己的依赖树，且可能包含文档、测试、多平台二进制（如 `@esbuild/darwin-arm64`）。

**Q：为什么 `import` 一个没在 `package.json` 里写过的包也能跑？**
因为扁平化安装可能让它作为"别人的依赖"躺在顶层，这叫**幽灵依赖（phantom dependency）**。pnpm 的严格结构能避免这个问题——这也是本项目 DSH profile 使用 pnpm 的原因之一。

**Q：删掉会怎样？**
源码、`package.json`、锁文件都还在，只要重新 `install` 即可恢复；但在恢复之前，任何 `import`、`npm run` 都会失败。

**Q：可以直接拷贝别人的 `node_modules` 吗？**
不推荐。里面含平台相关的二进制与绝对路径软链接，跨机器/跨系统容易失效，正确做法是拷 `package.json` + 锁文件后重新安装。

